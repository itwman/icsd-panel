# معماری پنل ICSD نسخهٔ ۲

## چرا بازنویسی

| نسخهٔ ۱ | نسخهٔ ۲ |
|---|---|
| فقط همان سروری را مدیریت می‌کرد که رویش نصب بود | یک پنل مرکزی، هر تعداد سرور |
| کاربر پنل با sudo می‌توانست `tee`، `chmod`، `rm` و `git` را با هر آرگومانی اجرا کند؛ نفوذ به پنل یعنی root | فاز ۱ کاملاً فقط‌خواندنی است؛ agent با کاربر بدون دسترسی و systemd محدود اجرا می‌شود |
| ۱۶ مسیر API بدون لاگین (مانیتورینگ، اطلاعات سیستم…) | همهٔ مسیرها نشست می‌خواهند؛ تست خودکار این را تضمین می‌کند |
| رمز پیش‌فرض `admin12345` | هیچ کاربر پیش‌فرضی نیست؛ مدیر با دستور روی سرور ساخته می‌شود |
| JWT در localStorage، HTTP روی پورت 8088 | کوکی HttpOnly + SameSite=Strict، فقط پشت HTTPS |
| 2FA اختیاری، کد قابل استفادهٔ دوباره | 2FA اجباری، هر کد فقط یک بار |
| بدون محدودیت تلاش ورود | ۸ تلاش برای هر نام کاربری و ۱۰ تلاش برای هر IP در ۱۵ دقیقه |
| رابط تک‌فایل وابسته به CDN و Google Fonts | همهٔ فایل‌ها محلی؛ CSP سخت‌گیرانه (`script-src 'self'`) |
| Nginx بومی روی 80/443؛ با سرورهای Docker تداخل داشت | پنل یا با systemd پشت یک vhost جدای nginx نصب می‌شود (`nginx -t` پیش از reload)، یا در Docker پشت Caddy؛ agent روی سرورهای مدیریت‌شده به وب‌سرور دست نمی‌زند |

## نمای کلی

```
مرورگر ──HTTPS──▶ nginx/Caddy ──▶ hub (FastAPI, یک پردازه)
                                  │  SQLite (WAL): کاربران، سرورها، تاریخچه، هشدارها
                                  │  حافظه: آخرین یک ساعت هر سرور
                                  ▼
          ◀──WSS (agent وصل می‌شود)── icsd-agent روی هر سرور
                                         /proc ،/sys، docker.sock (فقط GET)
```

- **جهت اتصال:** agent همیشه به hub وصل می‌شود. روی سرورهای مدیریت‌شده پورتی باز نمی‌شود و سرور پشت NAT یا فایروال هم کار می‌کند.
- **بافر:** اگر اتصال قطع شود، agent تا ۱۲۰ نمونه (حدود ۱۰ دقیقه) نگه می‌دارد و پس از وصل شدن می‌فرستد.

## agent (Go)

- یک فایل ایستا: حدود ۶ مگابایت، حدود ۱۵ مگابایت RAM، بدون cgo.
  - تنها وابستگی‌اش `coder/websocket` است که vendored شده؛ ساخت به proxy.golang.org نیاز ندارد.
- **هر ۵ ثانیه:**
  - CPU شامل user، system، iowait و **steal**؛ steal یعنی همسایه‌های VPS سهم CPU شما را می‌خورند.
  - load و RAM/swap بر پایهٔ `MemAvailable`.
  - نرخ خواندن و نوشتن دیسک‌ها (فقط دیسک‌های کامل، بدون شمردن دوبارهٔ پارتیشن‌ها).
  - نرخ شبکه (فقط کارت‌های فیزیکی؛ bridge و veth داکر حذف می‌شوند).
  - تعداد اتصال‌های TCP.
- **هر ۱۵ ثانیه:**
  - فضای پارتیشن‌ها و inodeها.
  - ۸ پردازهٔ پرمصرف از نظر CPU و ۸ پردازهٔ پرمصرف از نظر RAM. فقط نام کوتاه پردازه فرستاده می‌شود، نه خط فرمان، چون ممکن است رمز داشته باشد.
  - کانتینرهای Docker. فهرست از `docker.sock` و مصرف از فایل‌های cgroup (v1 و v2) خوانده می‌شود. `docker stats` برای هر کانتینر حدود یک ثانیه طول می‌کشد؛ cgroup چند میکروثانیه.
- **هویت:**
  1. agent توکن یک‌بارمصرف (۲۴ ساعته) را با یک رمز دائمی ۲۵۶ بیتی عوض می‌کند.
  2. hub فقط SHA-256 این رمز را نگه می‌دارد.
  3. رمز در `/etc/icsd-agent/agent.json` با دسترسی `0640 root:icsd-agent` ذخیره می‌شود.
- **حالت مدیریت (فاز ۲ تا ۴):** agent با root اجرا می‌شود و فقط کارهایی را انجام می‌دهد که `/etc/icsd-agent/policy.json` روی همان سرور اجازه داده است. hub نمی‌تواند این فایل را عوض کند؛ پس حتی hub نفوذشده هم از آن فراتر نمی‌رود. حالت `--monitor-only` همان رفتار فقط‌خواندنی فاز ۱ است.
- **امنیت فایل‌ها:**
  - هر مسیر با دنبال‌کردن symlinkها به مسیر واقعی تبدیل و با ریشه‌های مجاز مقایسه می‌شود.
  - حذف و تغییر نام روی خود ورودی انجام می‌شود؛ حذف یک لینک، مقصد آن را پاک نمی‌کند.
  - نوشتن ابتدا در فایل موقتی با نام تصادفی (`O_EXCL`) انجام می‌شود و مالک و دسترسی روی همان descriptor تنظیم می‌شود؛ پس symlink کاشته‌شده کارساز نیست.
  - zip/tar slip رد می‌شود.
  - `.ssh` حتی در آرشیو و بک‌آپ هم وارد نمی‌شود.
- **دیتابیس:**
  - بازگردانی فقط از پوشهٔ بک‌آپ انجام می‌شود.
  - MySQL با `--binary-mode` بازگردانی می‌شود تا فایل نتواند دستور سیستمی اجرا کند.
  - PostgreSQL در صورت امکان با نقش مالک دیتابیس بازگردانی می‌شود.
  - پیش از هر بازگردانی، خودکار یک نسخهٔ احتیاطی گرفته می‌شود.

## hub (Python)

- FastAPI، SQLite با WAL و یک اتصال. وابستگی‌ها: fastapi، uvicorn، bcrypt، httpx، segno (QR).
- **ذخیره‌سازی تاریخچه:**
  - یک ساعت آخر از حلقهٔ حافظه خوانده می‌شود: هر نمونه، حدود ۶۰ کیلوبایت برای هر سرور.
  - میانگین دقیقه‌ای ۱۵ روز نگه داشته می‌شود.
  - میانگین ساعتی ۴۰۰ روز نگه داشته می‌شود.
  - برای هر سرور در هر دقیقه فقط یک ردیف نوشته می‌شود، هر قدر هم که agent پرتکرار گزارش بدهد.
- **هشدارها:** وضعیت هر (قاعده، سرور، موضوع) در حافظه است و رخدادهای باز در دیتابیس.
  - هشدار وقتی فرستاده می‌شود که شرط به اندازهٔ «ماندگاری» ادامه پیدا کند. مثلاً CPU بالای ۹۰٪ به مدت ۱۰ دقیقه، نه یک جهش کوتاه.
  - پیام «رفع شد» یک بار فرستاده می‌شود.
  - پس از ری‌استارت hub، هشدارها دوباره فرستاده نمی‌شوند.
- **پایش آدرس‌ها** از خود hub انجام می‌شود: کد پاسخ، زمان پاسخ، عبارت مورد انتظار و انقضای SSL.
- **تأیید دوباره:** هر تغییر روی سرورها، کاربران، اعلان‌ها، قاعده‌ها و بک‌آپ‌ها یک کد تازهٔ رمز دوم می‌خواهد که ۱۵ دقیقه روی همان نشست معتبر است. کوکیِ دزدیده‌شده به‌تنهایی برای خرابکاری کافی نیست.
- **امنیت وب:**
  - کوکی HttpOnly/SameSite=Strict/Secure. در دیتابیس فقط هش نشست ذخیره می‌شود.
  - هدر `X-ICSD` و بررسی `Origin` روی هر درخواست تغییر‌دهنده.
  - CSP بدون `unsafe-inline`.
  - `/docs` (کاوشگر API) خاموش است.
  - گزارش فعالیت (audit) ثبت می‌شود.

## رابط کاربری

Preact + htm به شکل ماژول ES، بدون مرحلهٔ build، همراه با uPlot برای نمودار و فونت وزیرمتن. همه داخل مخزن‌اند.

- راست‌به‌چپ، اعداد فارسی، تاریخ شمسی (`Intl` مرورگر)، حالت روشن و تیره، سازگار با موبایل.
- کل رابط کمتر از ۳۰۰ کیلوبایت است.

## چرا سرور ایمیل نه

پیاده‌سازی سرور ایمیل روی VPS در عمل این مشکل‌ها را دارد:

- پورت 25 روی بیشتر ارائه‌دهنده‌ها بسته است.
- رکورد PTR و اعتبار IP لازم است.
- ایمیل‌ها به‌سادگی به Spam می‌روند و نگه‌داری Postfix/Dovecot/DKIM دائمی است.

راه درست: ایمیل را به یک سرویس بیرونی بسپارید. در فاز ۴، پنل فقط رکوردهای MX، SPF، DKIM و DMARC دامنه‌ها را بررسی می‌کند.
